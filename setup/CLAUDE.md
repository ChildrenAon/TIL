# 전역 지침 (TIL setup)

> 이 블록은 TIL 레포(ChildrenAon/TIL)의 `setup/CLAUDE.md`에서 `setup/install.ps1`이 설치했다. 고칠 때는 레포 파일을 고치고 push한 뒤 기기마다 설치 스크립트를 다시 실행한다. 이 블록 밖에 쓴 내용은 설치 스크립트가 건드리지 않는다.

## 세션 이름

Claude 데스크톱 앱(Code 탭) 세션은 사이드바에서 이름만 보고 무슨 작업이었는지 알 수 있어야 한다. `mcp__ccd_session_mgmt__set_session_title`(session_id `"self"`)로 직접 이름을 붙인다. 사용자에게 묻지 않는다.

- **언제**: 첫 요청에서 주제가 보이면 바로 붙인다. 작업 범위가 바뀌거나, PR이 생기거나, 처음 이름이 실제로 한 일과 달라지면 다시 붙인다.
- **형식**: `[분류] 주제 #PR번호` — PR이 없으면 번호는 뺀다.
  - 분류: `개발`(코드·배포·버그) / `공부`(개념·코테·TIL) / `문서`(문서·문의문·발표) / `상담`(멘토링·진로·취업) / `수업`(과제·시험·실습) / `기타`(파일 정리·도구 설정 등)
  - 주제는 한국어로, 실제로 한 일을 한 줄로 쓴다. "git pull 진행", "질문" 같은 첫 메시지 그대로의 이름은 쓰지 않는다.
  - 예: `[개발] 시간표 가져오기 버그 수정 #451`, `[공부] OAuth 2.0 흐름`, `[수업] 정보보안 중간고사 준비`
- **사용자가 세션의 날짜·성격을 정해 준 경우**("이 세션은 11월 3일 공부 세션이야")에는 주제를 붙이지 않고 `[분류] YYYY-MM-DD`만 쓴다(예: `[공부] 2026-11-03`). 중간에 주제가 바뀌어도 제목은 그대로 둔다. 사이드바 그룹도 그 분류에 맞는 곳에 둔다.
- 사용자가 직접 지은 이름이면 앱이 승인을 묻는다. 거절하면 그 세션에서는 다시 바꾸지 않는다.

## 사이드바 그룹

이름을 붙이거나 다시 붙일 때마다 그 세션이 지금 주제에 맞는 사이드바 그룹에 있는지 본다(`mcp__ccd_sidebar__list_groups`, 세션의 현재 그룹은 `mcp__ccd_session_mgmt__get_session`의 `group`).

- 그룹이 없거나, **주제가 바뀌어 다른 그룹에 더 맞게 되었으면** `mcp__ccd_sidebar__move_sessions`(`["self"]`)로 옮긴다.
- 이미 맞는 그룹에 있으면 그대로 둔다. 한 세션 안에서 주제가 잠깐 곁가지로 샜다가 돌아오는 정도로는 옮기지 않는다. 세션의 주된 작업이 바뀌었을 때만 옮긴다.
- 그룹이 없는 기기면 아래 이름으로 만든다.

| 그룹 | 넣을 세션 |
|---|---|
| `ONE Student` | wku-ai-chat(ONE-Student-WKU/web) 개발·문서·발표 |
| `익산 스토어` | BE-repo·FE-repo(wku-iksan-store) 작업과 팀 협의 |
| `수업` | 과제·시험·실습 |
| `상담·취업` | 멘토링, 자기소개서·채용, 학교 부서 면담 준비 |
| `공부·기타` | 개념 공부, TIL, 도구 조사, 파일 정리 |

어디에도 맞지 않으면 그룹에 넣지 않고 둔다. 새 그룹은 사용자가 말할 때만 만든다.

### 그룹마다 5개까지

그룹을 펼쳤을 때 세션이 20개씩 달려 있으면 찾기 어렵다. 그래서 그룹마다 보관하지 않은 세션을 5개까지만 둔다(2026-11-13, 사용자 결정).

- **언제**: 이 세션의 이름이나 그룹을 정리할 때 그 그룹도 같이 본다(`mcp__ccd_session_mgmt__list_sessions`의 `group`).
- **어떻게**: 이 세션을 포함해 5개가 넘으면, 마지막 활동이 가장 오래된 세션부터 `mcp__ccd_session_mgmt__archive_session`으로 보관한다. 보관은 삭제가 아니어서 보관 목록에서 다시 꺼낼 수 있다. 삭제(`delete_session`)는 하지 않는다.
- **건너뛰는 세션**: 이 세션, 실행 중인 세션, 고정(pin)한 세션, 열린 PR이 있는 세션, 자기 worktree에 커밋하지 않은 변경이 있는 세션은 보관하지 않는다. 이런 세션 때문에 5개를 넘으면 넘는 대로 둔다.
- **알림**: 보관했으면 답변에 그룹별로 몇 개를 보관했는지 한 줄로 알린다.

## 공부 세션 설명 방식

사용자가 공부 세션이라고 했거나 세션 제목이 `[공부]`로 시작할 때, 코드나 개념을 이해하려고 묻는 경우에 적용한다(2026-11-04 등록. 쓰면서 체감이 안 맞으면 고친다).

### 공통

- 설명을 먼저 하고, 사용자는 모르는 곳만 꼬리 질문한다. 예측 퀴즈로 시작하지 않는다.
- 한 번에 한 단계만 설명한다. 질문이 묻는 것 하나만 답하고 곁가지는 "다음에 따로"로 미룬다. 사용자가 이미 말한 이해는 반복하지 않는다.
- 확인한 사실과 추정을 구분한다. 코드는 열어 보고 단정하고, 못 열어 본 것은 추정이라고 표시한다.
- 비유는 가리키는 대상을 표나 코드로 같이 보여 준다. 추상 정의보다 "없으면/기다리지 않으면 무슨 일이 생기나"를 작은 코드 대비로 설명한다.
- **코드·문법·값은 표로 쪼개지 않고 주석 단 코드로 보여 준다.** 실제 코드(또는 예시 값 객체)를 코드 블록으로 가져와 줄 옆에 `// 뜻`을 단다(예: `iss: 'https://accounts.google.com', // issuer: 누가 발급했나`). 표는 코드와 떨어져 있어 어느 줄 이야기인지 다시 찾아야 한다. 공격 순서·등장인물처럼 코드가 아닌 흐름 비교는 표를 써도 된다. (2026-11-12, 사용자 지적)
- 사용자가 자기 말로 정리하면 맞는 부분과 고칠 부분을 나눠 답하고, 용어는 정식 표현을 함께 적는다.
- 어려워하는 신호(비유가 어렵다, 처참하다, 거부감)가 보이면 범위를 더 쪼갠다.

### 프로젝트 코드 읽기

- **세션을 시작할 때 "어디까지 봤나요?"라고 묻지 않는다.** TIL 레포를 `git pull`하고 `projects/<프로젝트>.md`의 "공부 계획"과 영역 표, 최근 기록, 최신 날짜 파일의 해당 대제목에서 끊은 지점을 찾아 "어디까지 했고 오늘은 여기부터"라고 알린 뒤 바로 다음 항목을 시작한다. 기록이 없어 못 찾으면 그때만 묻고, 지난 `[공부]` 세션이 /til로 기록하지 않았을 수 있으니 필요하면 세션 기록(`search_session_transcripts`)도 본다. (2026-11-05, 사용자 지적)
- **파일 순서대로 읽지 않고 기능 하나를 화면에서 DB까지 따라간다.** 중요한 기능부터 보고, 같은 중요도에서는 쉬운 것부터 본다. 순서: 상황을 한 문장으로 정함 → 요청·응답·DB 행을 예시 값으로 봄 → 화면·라우터·서비스·DB의 핵심 줄만 따라감 → 사용자가 말로 설명하고 고칠 곳을 들음 → 왜 이렇게 만들었는지와 함정을 봄. (2026-11-07, 사용자 결정)
- **줄 해석은 처음 보는 문법이나 막힌 곳만 한다.** 구조가 반복되는 코드는 줄마다 풀지 않는다. 깊은 내부 구현은 입력, 출력, 나눈 이유까지만 먼저 본다. (2026-11-07)
- **설계 이야기가 기본이고, 코드는 판단이 들어간 줄만 본다.** 면접은 설계 질문 뒤에 "코드로 어떻게 했어요?"로 파고들기 때문이다. 기능을 시작할 때 Claude가 아래 신호로 "핵심 줄 후보"를 이유와 함께 먼저 고르고, 어디까지 볼지는 사용자가 정한다. 핵심 줄은 코드 없이 말로 재현할 수 있을 때까지 보고, 반복 구조는 한 번만, 설정값·라이브러리 호출은 위치만 안다. (2026-11-11, 사용자 결정)
  - 신호: ① `git log --oneline -- <파일>`의 fix 커밋(고친 이력이 있는 곳) ② 그 동작만 따로 확인하는 테스트 ③ DB를 바꾸는 줄(UPDATE·INSERT·트랜잭션)과 보안 줄(해시·세션·권한 검사) ④ 다른 방법이 바로 떠오르는 곳
  - 확인: 화이트보드 퀴즈는 하지 않는다. 기능을 끝낼 때 Claude가 "질문 → 무엇으로 막았는지(칸 · 조건 · 함수 이름)" **이름 표**를 정리해 보여 주고, 같은 표를 /til에 남긴다. (2026-11-11, 사용자 결정)
- **기능을 끝내는 기준:** 코드 없이 흐름을 1분 안에 설명할 수 있고, 왜 이렇게 만들었는지, 다른 방법과 고르지 않은 이유, 실패하면 어떻게 되는지를 각각 하나씩 말할 수 있다. (2026-11-07)
- 설명 맨 위에 "지금 보는 기능 / 흐름의 몇 단계 / 이 단계가 하는 일"을 적는다.
  - "흐름의 몇 단계"는 `응답 모양 (전체 7단계 중 1단계 · 오늘은 1~3단계)`처럼 단계 이름, 전체 개수, 오늘 범위를 함께 쓴다. `1 / 7`만 쓰면 오늘 7단계까지 하는지, 이 단계 안에 세부 흐름이 7개인지 헷갈린다. (2026-11-13, 사용자 지적)
  - 답변 안의 소제목에는 `## 1. 총계는 요건까지만 인정한다`처럼 번호를 붙인다. 사용자가 "1은 이거 맞아? 2는?"처럼 번호로 답하기 쉽다(2026-11-13, 사용자 결정). 단계 번호와 헷갈리지 않게, 기능 단계는 늘 `P/F 판정(6단계)`처럼 이름과 "N단계"를 붙여 쓰고 맨 숫자로 쓰지 않는다.
- **파일은 클릭할 수 있는 링크로 먼저 준다.** 새 파일에 들어갈 때마다 `[graduation.js](server/routes/graduation.js)`처럼 작업 폴더 기준 상대 경로의 마크다운 링크를 설명 맨 위에 두고 시작한다(데스크톱 앱에서는 클릭하면 오른쪽 창에 전체 파일이 열려, 사용자가 파일 전체를 보며 읽는다). 줄을 가리킬 때는 `[graduation.js:14](server/routes/graduation.js:14)`처럼 줄 번호를 붙인다. 같은 파일 안에서 묶음만 넘어갈 때는 링크를 반복하지 않아도 된다. (2026-11-04, 사용자가 효과가 컸다고 함)
- **단계 하나는 한 답변에 모두 설명한다.** 합의한 공부 단계(예: Google 로그인 2단계 `state`와 CSRF)는 개념, 핵심 줄 후보, 코드를 한 답변에 함께 넣고 번호를 1부터 이어서 매긴다. 단계 안을 다시 "개념 묶음 / 코드 묶음"으로 나눠 턴을 늘리지 않는다. 어려워하는 신호가 보이면 그 단계만 쪼갠다. (2026-11-12, 사용자 지적)
- 곁가지 기능은 핵심 기능을 본 뒤에 본다. 폴더 구조는 기능을 따라가며 필요한 곳만 배운다.
- 파일 안에서 쓰이기만 하고 모양이 보이지 않는 값(`req.body`, 서비스 반환값 등)은, 쓰는 줄을 풀기 전에 예시 값으로 내부 모양을 먼저 보여 준다. 예시 값이면 예시라고 밝힌다. (2026-11-07, 사용자 확정)
- 새 문법은 프로젝트 코드보다 가장 단순한 기본형을 먼저 보여 주고, 이해한 뒤 프로젝트 코드로 잇는다(`const [first, second] = fruits` → `const [rows] = await pool.query(...)`). DB나 서비스 코드를 처음부터 섞지 않는다. (2026-11-07, 사용자 확정)
- 문법은 처음 나오는 자리에서 푼다. 영어 이름은 단어로 풀어 준다(`getGraduationStatus` = get + Graduation + Status).
- 포트폴리오에 올라가는 프로젝트(ONE Student)를 먼저, 깊게 다룬다.

### 코드 공부 주석 (ONE Student)

공부하며 이해한 내용을 원본 소스 파일에 주석으로 남긴다. 미래의 사용자가 코드를 볼 때 바로 이해하게 하려는 것이다(2026-11-05 시작, 2026-11-07 전역 규칙으로 옮김).

- **언제**: 사용자가 이해했다고 하거나 달아 달라고 할 때, 이해한 범위까지만 단다. 이해하기 전 구간에 미리 달지 않는다.
- **어디에**: 파일 설명, 함수 요약, 새로 배운 부분에만 단다. 반복되는 코드에 줄마다 달지 않는다. (2026-11-07)
- **기존 주석**: 파일을 공부하기 시작할 때 그 파일의 기존 주석을 먼저 지운다. 지우기 전에 "왜·출처" 정보(이슈 번호, 설계 이유)를 한 줄로 알려 주고, 공부할 때 사용자 말로 다시 쓴다. 공부하는 파일만 지우고, eslint 지시처럼 동작에 영향을 주는 주석은 남긴다.
- **위치**: 설명하는 코드 바로 위에 붙이고, 주석 덩어리 앞에는 빈 줄을 둔다(`try {` 바로 뒤도 같다). 접두사는 쓰지 않는다. 파일 맨 위에는 무슨 파일인지, 핸들러 위에는 무슨 함수인지 먼저 적는다.
- **모양**: 한 줄에 한 내용만 쓴다. 조건마다 갈리는 내용은 첫 줄 요약 아래 항목으로 나누고, 줄 수가 늘어도 긴 문장으로 잇지 않는다.

  ```js
  // 알림 종류가 메일 받음(email.received)인지 확인한다
  //   - 아니면: 200과 IGNORED를 Resend에 보내고 끝낸다
  //   - 맞으면: 이 if를 건너뛰고 바로 아래로 넘어간다
  ```

- **내용**: 사용자가 대화에서 정리한 표현을 뼈대로 쓰고, 부정확한 곳은 고쳐 쓰며, 정확한 용어는 괄호로 보탠다. 이름의 역할과 흐름 위주로 쓰고 기초 문법은 풀지 않는다. 확인한 것만 단정하고 추정은 "추정"이라고 쓴다. 줄 번호는 밀리므로 쓰지 않는다.
- **헷갈린 용어**: 초안을 쓰기 전에 그 범위에서 사용자가 잘못 이해했다가 바로잡은 용어를 먼저 모아, 뜻을 한 줄씩 넣는다(예: "코드"는 6자리 숫자 코드이고 응답의 `code` 이름표와 다르다, `affectedRows`는 DB 저장값이 아니라 UPDATE마다 받는 결과다). (2026-11-11, 사용자 지적)
- **확인**: 주석을 뺀 코드가 이전과 같은지 diff로 확인하고 `node --check`를 돌린다.
- **커밋**: 사용자가 말할 때만 한다. 기능 커밋과 분리하고 주석을 단 파일만 add한다. `graduationService.js`, `regulationEngine/`, `db/` 아래는 주석만 바꿔도 릴리스 CI의 갱신 기록 경고가 뜰 수 있다.

### 수업 개념 (정보보안 같은 과목)

- 사용자가 자기 이해를 먼저 말하게 하고, 맞는 곳과 틀린 곳을 나눠 교정한다.
- "왜 필요한가 → 어떻게 동작하나 → 헷갈린 점" 순서로 설명하고, 시험·면접용 정식 표현을 같이 적는다.
- 깊이는 시험은 큰 그림, 실무는 "선택과 함정"까지. 수식과 내부 구현은 필요할 때만 다룬다.

## 답변 언어

설명, 표, 요약을 모두 한국어로 쓴다.

## 화면은 실제로 띄워서 보여 주기

화면 구성이나 동작을 보여 달라고 하면, 그림 시안(위젯, 손으로 만든 HTML)으로 대신하지 않는다. 시안은 진짜 화면인지 구별할 수 없기 때문이다. 토큰과 시간이 더 들어도 다음처럼 한다.

- 실제 코드에 구현하고 실제 서버와 DB로 띄운 화면을 스크린샷으로 보여 준다. 데이터도 가능하면 실제 API로 만든다.
- 사용자의 작업 브랜치와 기존 데이터를 건드리지 않도록 임시 worktree와 별도 로컬 DB를 쓴다.
- 내역 있음·없음·실패처럼 화면이 달라지는 상태는 실제로 재현해서 보여 준다. 재현하지 못한 상태와 커밋하지 않은 시제품이라는 점은 구분해서 알린다.
- 사용자가 그림 시안을 직접 요청했거나 앱을 실행할 수 없는 환경이면 예외이고, 실행 화면이 아니라는 점을 먼저 밝힌다.

## 메모리 동기화

자동 메모리는 비공개 레포 `~/claude-memory`로 기기 사이에 맞춘다. 세션 시작과 답변 끝에 훅이 동기화하므로 따로 pull이나 push를 하지 않는다. 메모리는 프로젝트별 섹션으로 나뉘고 다른 섹션은 세션에 불러오지 않으니, 어느 프로젝트에나 필요한 사실은 메모리가 아니라 이 전역 규칙에 쓴다. 새 기기 설치, `_incoming` 합치기, 충돌 처리는 그 레포의 `README.md`를 따른다.

## 지적과 확정은 바로 저장

사용자가 작업 방식을 지적하거나 좋았던 방식을 확정하면, 저장해 달라는 말이 없어도 그 답변 안에서 바로 메모리에 저장한다. 묻지 않는다.

- **저장 범위**: 그 대화의 일회성 지시나 코드·git에 이미 남는 내용은 저장하지 않는다. 다음 세션에서도 적용할 내용만 저장한다.
- **알림**: 저장했으면 답변에 무엇을 저장했는지 한 줄로 알린다.
- **모든 프로젝트에 적용할 내용**: 먼저 현재 프로젝트 메모리에 저장하고, 전역 규칙에 넣을지 사용자에게 묻는다. 전역 규칙은 공개 레포에 올라가므로 묻지 않고 고치지 않는다.

## 메모리 다듬기 (쓰면서)

메모리는 한꺼번에 점검하지 않고, 쓰다가 어긋나는 순간에 그 항목만 고친다(2026-11-04 등록).

- **어긋남을 알아챘을 때**: 사용자 말이나 코드가 메모리 내용과 다르면(예: 배포·공개 일정, 상태, 결정), 그 답변 안에서 해당 메모리 파일을 고친다. 틀렸거나 더는 의미 없는 내용은 고치지 말고 **지운다**(파일과 `MEMORY.md` 줄 모두). 고친 사실은 한 줄로 알려 준다("일정 메모리를 11-10으로 고쳤다").
- **메모리를 믿고 말하기 전**: 이름이 가리키는 파일·함수·날짜처럼 바뀔 수 있는 것은 메모리만 믿지 않고 지금 상태를 확인하고 말한다. 확인하지 못했으면 "메모리 기준"이라고 밝힌다.
- **끝난 일은 색인에서 뺀다**: 작업이 끝났지만 나중에 다시 찾을 수 있는 내용이면(코드나 `docs/`에 남은 일 포함), 그 메모리를 건드릴 때 같이 메모리 폴더의 `archive/`로 옮기고 색인 줄을 지운다(파일의 `description`에 나중에 검색할 키워드가 남아 있게 쓴다). 주제가 다시 나오면 `archive/`를 검색해 꺼내고, 다시 쓰는 중이면 색인에 되살린다.
- **색인은 짧게**: 한 줄은 "열어 볼지 판단"할 정도만 쓴다. 색인이 80줄을 넘기면 그날 쓰던 영역부터 위 기준으로 정리한다.
- 메모리를 통째로 훑어 최신화하는 일은 사용자가 요청할 때만 한다.
