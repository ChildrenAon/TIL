# /til — 오늘 배운 것 정리해 올리기

하루에 몇 번이든 부를 수 있다. 사용자가 공부하다 생각날 때 부르는 "저장" 버튼처럼 동작한다. 정리는 Claude가 하고 **올리기 전에 묻지 않고 바로 올린다**(2026-11-03부터). 채팅에서는 마크다운이 렌더되지 않아 초안이 읽기 어렵기 때문에, 사용자가 GitHub에서 결과를 보고 피드백하는 방식이다. 사용자가 고쳐 달라고 한 방식은 `setup/til-style.md`에 쌓아서 다음부터는 처음부터 그 방식으로 쓴다. 바로 올리는 만큼 5단계(공개 레포 금지)를 올리기 전에 꼼꼼히 본다.

## 0. 레포 준비

1. 이 스킬 폴더의 `repo_path.txt`에 TIL 로컬 경로가 한 줄로 있다. 없거나 그 폴더가 없으면 `gh repo clone ChildrenAon/TIL "$HOME/TIL"`로 받고 그 경로를 `repo_path.txt`에 적는다.
2. 그 경로에서 `git pull --rebase`로 최신 상태를 받는다. 다른 컴퓨터에서 쓴 기록이 있을 수 있다.
3. 오늘 날짜(사용자 로컬 기준) 파일 `YYYY/Month/MM-DD.md`, `glossary.md`, `setup/til-style.md`를 읽는다.
4. **`setup/til-style.md`가 이 스킬의 기본 규칙보다 우선한다.** 사용자가 직접 고쳐 달라고 해서 쌓인 규칙이기 때문이다.

## 1. 무엇을 기록하나

이 대화에서 **사용자가 새로 알게 된 것**만 고른다.

- 사용자가 묻고 설명을 들은 개념
- 겪은 문제와 해결 과정, 그 방법을 고른 이유, 검토했다가 버린 방법과 이유
- 코테를 풀다 막혔던 지점과 새로 안 문법·자료구조·아이디어

기록하지 않는 것:
- Claude가 대신 한 작업 결과 자체(파일을 옮겼다, 커밋했다). 그 과정에서 사용자가 이해한 게 있으면 그것만 쓴다.
- Claude가 설명만 하고 사용자가 이해했는지 드러나지 않은 것은 바로 넣지 않는다. 파일에는 넣지 않고, 올린 뒤 결과 보고에 "이해 확인 필요" 후보로 알려 사용자가 원하면 다음에 올린다. TIL은 "이제 내가 설명할 수 있는 것"의 기록이다.
- 사용자가 이미 알고 있던 것, 잡담
- **오늘 파일에 이미 있는 내용.** 같은 대화에서 /til을 다시 부르면 그 뒤에 새로 배운 것만 추가한다.

새로 배운 게 없으면 아무것도 쓰지 않고 "이번에는 기록할 새 내용이 없다"고만 말한다.

## 1-1. 모아 보기 모드 — 다른 세션에서 배운 것 모으기

`/til 모아`라고 하거나, 첫 요청에 `[TIL 모아 보기]`가 있는 예약 작업(매일 새벽 5시)이면 지금 대화 대신 **이 컴퓨터의 다른 세션들**을 본다. 개발·수업 세션에서 물어보다 알게 된 것을 `/til` 없이 넘어간 날을 위한 것이다.

1. 0단계(레포 준비)를 한다.
2. `node "<레포>/setup/collect-sessions.js" --out "<임시 폴더>/til-collect.md"`를 실행한다(임시 폴더는 스크래치패드나 `$env:TEMP`). 마지막으로 모은 시각 이후의 대화만 나온다. 세션에서 `/til`을 이미 했으면 그 뒤 대화만, 모아 보기 세션 자신은 빼고, 이어 하기로 복사된 대화는 한 번만 싣는다.
3. 출력 첫 줄들의 `세션 0개`이면 4의 "없음"으로 간다. 아니면 파일을 읽는다(크면 나눠 읽는다).
4. 1단계 기준으로 고른다. 여기에 더해:
   - **공부·개발·수업과 관계없는 대화는 통째로 건너뛴다**(집·가족·연애·통화 내용, 일정 조율, 발표 섭외처럼 사람 사이의 일). 그 세션이 있었다는 것도 초안에 쓰지 않는다.
   - Claude가 혼자 한 작업 보고(PR 만들었다, 테스트 통과)는 빼고, 사용자가 묻고 이해한 것·고른 이유·버린 방법만 남긴다. 개발 세션은 프로젝트 대제목(`# ONE Student` 등) 항목이 되기 쉽다.
   - 각 요청 머리의 `[YYYY-MM-DD]`가 그 대화의 날짜다(새벽 5시 전은 전날). 그 날짜 파일에 쓴다. 날짜가 여럿이면 파일도 여럿이다. 그 날짜 파일에 이미 있는 내용은 뺀다.
   - 5단계(공개 레포 금지)를 특히 꼼꼼히 본다. 다른 세션에는 사람 이름·학교 답변·운영 값이 많다.
5. 결과에 따라:
   - **없음**: 아무것도 쓰지 않고 `node "<레포>/setup/collect-sessions.js" --mark <출력의 UNTIL 값>`으로 여기까지 봤다고 기록한다. 예약 작업이면 알림을 보내지 않고 "기록할 새 내용 없음" 한 줄로 끝낸다.
   - **있음**: 7단계처럼 초안을 보여 준다. 항목마다 어느 세션에서 나왔는지 세션 제목을 한 줄 붙인다(초안에만, 파일에는 쓰지 않는다). 예약 작업이면 `PushNotification`으로 "어제 TIL 초안 N개 — 세션을 열어 확인하면 올립니다"를 보내고 답을 기다린다. 사용자가 답할 때까지 `--mark`하지 않는다. 답이 오지 않은 채 다음 날 모아 보기가 돌면 그 내용까지 다시 모아 한 번에 묻는다.
6. 사용자가 올리라고 하거나(9단계 push 뒤) 올리지 말라고 하면 그때 `--mark <UNTIL>`을 한다. push 직전에는 `git pull --rebase` 후 날짜 파일을 다시 읽어, 그 사이 다른 세션에서 이미 올린 항목은 뺀다.

세션 기록은 컴퓨터마다 따로 있어서, 각 컴퓨터의 모아 보기는 그 컴퓨터에서 한 대화만 본다. 마지막으로 모은 시각은 `~/.claude/til-collect-state.json`에 있다.

## 2. 어디에 쓰나 — 날짜별

- 파일: `YYYY/Month/MM-DD.md` (하루에 하나). `Month`는 영어 월 이름이다(`2026/November/11-03.md`, `2026/June/06-22.md`). 없으면 만들고 맨 위에 날짜가 든 목차(`> **YYYY-MM-DD 목차**`)를 쓴다. 날짜 제목(`# YYYY-MM-DD`)은 쓰지 않는다. 대제목이 가장 큰 `#`여야 하기 때문이다.
- 하루 파일은 **대제목**(`#`)으로 나눈다. GitHub는 글자 크기를 정할 수 없고 제목 단계로만 정해지므로, 대제목을 가장 큰 `#`로 쓰고 한 단계씩 내려 항목은 `##`, 항목 안 소제목은 `###`로 쓴다. 대제목 하나가 그날 다룬 주제 하나이고, 서로 다른 주제는 섞지 않는다. `[개념]` 같은 꼬리표는 쓰지 않는다. 대제목이 곧 구분이다.
  - 공부한 과목·분야: `# 정보보안`, `# 네트워크` …
  - 프로젝트: 프로젝트 이름 그대로 `# ONE Student`, `# 익산 스토어` (프로젝트 지도 페이지 이름과 맞춘다)
  - 코테: `# 코테`
  - 대제목과 대제목 사이에는 여백을 넉넉히 둔다. 앞 대제목의 마지막 내용 뒤에 빈 줄로 감싼 `<br>` 열 줄(한 줄에 `<br>` 하나씩 연달아)을 넣고 다음 `# 대제목`을 쓴다(맨 위 목차와 첫 대제목 사이에는 넣지 않는다). 새 대제목을 끼워 넣을 때도 앞뒤 여백을 지킨다.
  - 순서는 항상 프로젝트(ONE Student → 익산 스토어) → 수업 과목 → 코테다. 하루 파일 본문과 맨 위 목차, README 목차가 같다. 새 항목이 들어갈 때 이 순서에 맞는 자리에 끼워 넣는다.
  - 이미 쓴 대제목은 README 목차에서 찾아 같은 이름으로 쓴다. 새 대제목을 만들었으면 결과 보고에 "새 대제목"이라고 밝혀, 이름은 피드백으로 고친다.
- 대제목 아래 항목 하나는 `## 번호. 제목`이다(`## 1. 전자서명`). 번호는 대제목마다 1부터 시작하고, 같은 날 같은 대제목에 항목을 더 쓰면 이어서 붙인다. 제목에 프로젝트 이름이나 꼬리표를 반복하지 않는다. 항목 안 소제목은 `###`다.
- 한 대제목에 항목이 2개 이상이면 대제목 바로 아래에 흐름을 둔다. 항목을 추가할 때마다 이어서 고친다.
  ````markdown
  # 정보보안

  > **흐름**: 이 순서로 이어서 배웠다

  ```mermaid
  flowchart LR
    A["전자서명"] -->|"공개키를 어떻게 믿나?"| B["전자인증서"]
    B -->|"검증은 어떤 순서로?"| C["발급과 검증 순서"]
  ```
  ````
  라벨은 큰따옴표로 감싸고 줄바꿈은 `<br/>`. 간선 라벨에는 "왜 다음으로 넘어갔나"를 질문으로 적는다.
- 파일 맨 위에 **목차**를 항상 둔다(머리에 날짜). 열자마자 무엇을 공부했는지 색인처럼 보이게 한다. 항목을 추가할 때마다 목차에도 한 줄 추가하고, 새 대제목이면 대제목 줄도 만든다. 요약은 항목의 한 줄 결론을 20자 안팎으로 줄인 것이다. 앵커는 소문자, 공백→하이픈.
  ````markdown
  > **2026-11-03 목차**
  >
  > **[정보보안](#정보보안)**
  > 1. [전자서명](#1-전자서명) — 해시에 개인키로 서명, 공개키로 검증
  > 2. [전자인증서](#2-전자인증서) — 공개키가 그 사람 것임을 CA가 보증
  >
  > **[ONE Student](#one-student)**
  > 1. [재시딩 중 검색 공백 없애기](#1-재시딩-중-검색-공백-없애기) — 임베딩을 먼저 받고 한 트랜잭션으로 교체
  ````
- 같은 주제를 전에 기록했으면(다른 날 파일, README 목차로 찾는다) 새 항목 끝에 `이전 기록: [YYYY-MM-DD 제목](../../YYYY/Month/MM-DD.md#번호-제목)` 링크를 단다(예: `#1-전자서명`). 옛 파일은 고치지 않는다.

## 3. 항목 템플릿

대화에 근거가 없는 칸은 지운다. 빈칸을 지어내서 채우지 않는다. 짧아도 된다.

모든 항목은 같은 뼈대를 따른다: **`## 번호. 제목` → 맨 위 `> **한 줄 결론**` 인용 블록 → `###` 소제목 구간 → 헷갈린 점은 경고 박스**. 비교는 표, 순서·구조는 도식(코드 블록 또는 mermaid)으로 쓴다. 굵은 글씨는 핵심 용어에만 쓴다. 자세한 규칙은 `setup/til-style.md`의 "대제목과 번호", "읽기 쉬운 구조".

항목 종류는 대제목이 정한다. 과목·분야 대제목이면 개념 항목, 프로젝트 대제목이면 프로젝트 항목, `# 코테`면 코테 항목이다.

**프로젝트 항목** (`# ONE Student`처럼 프로젝트 이름 대제목 아래)
````markdown
## 번호. 한 줄 제목

> **지도에서 위치**: [프로젝트명 지도](../../projects/<이름>.md) › 영역 › 기능
> **한 줄 결론**: (대화에서 사용자가 정리한 문장이 있으면 그대로)

### 문제
### 해결
(순서·구조는 도식, 전후 비교는 표)
### 왜 이 방법을 골랐나
### 검토했지만 버린 방법과 이유
| 방법 | 버린 이유 |
|---|---|

### 면접에서 설명한다면
(3문장 이내)

관련: PR·이슈 링크(공개 레포일 때만)
이전 · 다음 기록: 같은 영역의 링크
````

**개념 항목** (`# 정보보안`처럼 과목·분야 이름 대제목 아래)
````markdown
## 번호. 개념 이름

> **한 줄 결론**: (내 말로. 대화에서 사용자가 정리한 문장이 있으면 그대로)

정식 표현: …
어디서 마주쳤나: … (있을 때만)

### 왜 필요한가
(없으면 어떤 문제가 생기나)
### 어떻게 동작하나
(비교는 표, 순서·구조는 도식·짧은 예시 코드)
### 헷갈린 점
> [!WARNING]
> (가장 헷갈렸던 한 가지를 굵게 시작해서 쓴다)

출처: (문서 링크가 있으면)
````

**코테 항목** (`# 코테` 아래)
````markdown
## 번호. [사이트 번호] 문제 이름

> **한 줄 결론**: 핵심 아이디어 한 문장
> 유형 / 난이도

### 처음 접근과 막힌 지점
### 핵심 아이디어
### 코드
(핵심 부분만)
### 새로 알게 된 것
````

## 4. 워딩 — 사용자가 다시 읽고 바로 이해할 수 있게

- **사용자의 표현을 먼저 쓴다.** 질문할 때 쓴 말, "그러니까 ~라는 거지?"로 확인한 문장, 이해가 된 계기가 된 비유를 살린다. 교과서식 일반론으로 바꾸지 않는다.
- 넣기로 한 항목에서 사용자가 더 묻지 않고 넘어간 설명은 이해한 것으로 보고, 대화에서 나온 설명을 그대로 쓴다.
- 개념은 "내 말로"와 "정식 표현"을 둘 다 남긴다. 면접에서는 정식 표현을 써야 하기 때문이다.
- `glossary.md`에 있는 용어는 거기 적힌 "내 말로"와 같은 말로 쓴다. 새 용어가 나오면 표 맨 아래에 한 행 추가한다: `| 용어 | 내 말로 | 정식 표현 | [YYYY-MM-DD](YYYY/Month/MM-DD.md) |`
- 문체는 짧은 평서문 메모체("~다", "~함")로 쓴다. 한국어로 쓰고, 영어 용어는 처음 나올 때 한 번 괄호로 붙인다.
- 강약을 둔다. 모든 줄이 같은 모양이면 읽히지 않는다: 주제는 대제목(가장 큰 `#`), 항목은 번호(`##`), 결론은 인용 블록, 구간은 `###`, 비교는 표, 순서는 도식, 헷갈린 점은 경고 박스, 굵은 글씨는 핵심 용어에만.

## 4-1. 프로젝트 지도

프로젝트 대제목 아래 항목은 맨 처음 보는 사람이 "이게 뭔 프로젝트고 구조에서 어디쯤이지?"를 알아야 읽힌다. 그래서 프로젝트마다 지도 페이지 `projects/<영문-소문자>.md`를 하나 둔다(`projects/one-student.md`).

- 구성: 한 줄 소개 → 구조 도식(mermaid) → 영역 표(영역 / 위치 / 하는 일 / 공부 상태 / 관련 기록) → 용어는 `glossary.md`로 링크.
- 프로젝트 대제목에 항목을 올릴 때 지도 페이지가 없으면 틀부터 만든다. 있으면 영역 표의 "공부 상태"와 "관련 기록"을 그 항목에 맞게 갱신한다. 초안에도 지도 변경을 같이 보여 준다.
- 모르는 칸은 지어내지 않는다. 확인한 것만 쓰고 나머지는 "아직"으로 둔다.
- 5단계(공개 레포 금지)는 지도에도 그대로 적용된다. 구조와 이름만 쓰고 운영 값·개인정보·팀원 실명은 넣지 않는다.

## 5. 공개 레포다 — 넣지 않는 것

- 학교·기관에 문의해 받은 답변 원문, 담당자 이름·연락처, 문의 내용 그대로
- 운영 환경 값: 내부 URL·DB 이름·환경변수 값·서버 주소, API 키·토큰·비밀번호
- 사용자·학생 개인정보, 성적, 계정 정보
- 팀원 실명, 회사·팀 내부 정보, 비공개 레포 코드 통째 (핵심 몇 줄만, 이름은 일반화)

애매하면 일반화해서 쓴다. 예: "교육혁신과 답변에 따르면 …" → "학교에 확인해 보니 …".

## 6. README 목차

`README.md`의 목차는 대제목별로 나뉘어 있다(`### 정보보안`, `### ONE Student` …). 항목이 속한 대제목 아래 **맨 위**에 새 항목 한 줄씩 추가한다. 새 대제목이면 `### 새 대제목` 구간을 순서(프로젝트 → 수업 과목 → 코테)에 맞는 자리에 만든다.

`- YYYY-MM-DD [제목](YYYY/Month/MM-DD.md#번호-제목)`

앵커는 GitHub 규칙(소문자, 공백→하이픈, `[]`·`—`·`.`·`,` 등 문장부호 제거)으로 만든다. 번호 항목이라 `## 1. 전자서명`의 앵커는 `#1-전자서명`이다.

새 프로젝트 지도 페이지를 만들었으면 README의 `## 프로젝트 지도` 목록에도 한 줄 추가한다.

## 7. 확인 없이 바로 올린다

`/til`(지금 대화 모드)은 올리기 전에 "이렇게 올려도 될까요?"를 묻지 않는다. 채팅에서는 마크다운이 렌더되지 않아 초안을 읽기 어렵고, 사용자가 GitHub에서 결과를 보며 피드백하기로 했다(2026-11-03).

1. 파일을 바로 쓴다: 오늘 파일(본문, 대제목 아래 흐름, 맨 위 목차), `README.md` 목차, `glossary.md`, 프로젝트 지도.
2. 5단계(공개 레포 금지)를 쓰는 중에 먼저 점검한다. 묻지 않는 만큼 애매한 값은 일반화하거나 뺀다.
3. "이해 확인 필요" 후보는 파일에 넣지 않는다. 올린 뒤 결과 보고에 알린다.
4. 9단계로 커밋·push한다.

**예외 — 모아 보기 모드(1-1)**: 사용자가 자리에 없고 다른 세션의 내용이 섞이므로, 기존대로 초안을 만들어 알림을 보내고 확인받은 뒤 올린다.

## 8. 피드백 — 사용자가 GitHub에서 본 뒤

- 사용자가 결과를 보고 고쳐 달라고 하면 파일을 고쳐 다시 push한다. 고칠 때마다 이 요청이 **이번 항목만의 수정**인지 **앞으로도 적용할 스타일**인지 판단한다.
  - 사실 오류, 이 항목에만 해당하는 내용 → 그 항목만 고친다.
  - 문체, 길이, 칸 구성, 표현 습관, 넣고 빼는 기준처럼 다음 기록에도 해당하는 것 → 고치고 `setup/til-style.md`에 규칙 한 줄을 추가한다(`- 규칙 (YYYY-MM-DD)`). 결과 보고에 "스타일 규칙에 추가함: …"이라고 알려서 사용자가 아니라고 할 수 있게 한다.
  - 둘 중 어느 쪽인지 애매하면 스타일로 넣지 않고 그 항목만 고친다.
- 올린 것을 취소하라고 하면 해당 항목을 지우는 커밋을 올리고, 그 사이 `til-style.md`에 추가한 규칙도 되돌린다.
- 사용자가 GitHub에서 직접 고친 내용은 존중한다. 다음 기록 전에 `git pull --rebase`로 받고, 충돌하면 사용자의 변경을 살린다.

## 9. 커밋·push

1. 바꾼 파일만 `git add`한다(오늘 파일, README, glossary, 바뀌었으면 `setup/til-style.md`).
2. 커밋 메시지: `til: YYYY-MM-DD 제목1, 제목2` (스타일 규칙이 바뀌었으면 본문에 `style: …` 한 줄)
3. `git push`. 거부되면 `git pull --rebase` 후 한 번 더 push한다. 그래도 실패하면 이유를 알리고 로컬 커밋은 남긴다.

`til-style.md`는 레포 파일이라 다른 컴퓨터에서도 다음 `/til`의 `git pull`로 바로 반영된다. 스킬을 다시 설치할 필요가 없다.

## 10. 알리기

올린 항목 제목과 GitHub 파일 링크(`https://github.com/ChildrenAon/TIL/blob/main/YYYY/Month/MM-DD.md`)만 짧게 알린다. 본문 전체를 채팅에 다시 붙이지 않는다. 있으면 한 줄씩 덧붙인다: 새 대제목, 제외한 "이해 확인 필요" 후보, 새로 추가한 스타일 규칙.
